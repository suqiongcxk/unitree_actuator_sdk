# 基于微信小程序与 RK3588 的四足机器人无线遥控系统项目计划书

> 文档版本：V2.0  
> 项目对象：12 自由度四足机器人  
> 控制终端：微信小程序（横屏）  
> 机器人主控：RK3588  
> 控制方式：强化学习速度控制 `vx / vy / wz`  
> 文档状态：总体架构与实施计划  
> 原则：先打通最小闭环，再逐步增加遥测、认证、生产化能力

---

# 0. 本版修订重点

本版在原计划基础上重点做以下调整：

1. **进一步明确项目边界**：整个遥控系统分为“小程序端”和“RK3588 机器人端”两大部分，MuJoCo 与真实机器人只作为机器人端的不同执行后端。
2. **调整实施顺序**：当前小程序横屏 UI、双摇杆、Mock、基础 WebSocket 协议已经完成，因此后续不再从 UI Mock 重新开始，而是优先完成：
   - 协议冻结；
   - 小程序 ↔ WebSocket 本机闭环；
   - 小程序 ↔ MuJoCo 端到端控制；
   - RK3588 部署；
   - 实机低速联调。
3. **连接状态与机器人状态分离**：网络连接状态不再混入机器人运动状态，分别建立 Connection State 与 Robot State。
4. **新增控制权机制**：一个机器人同一时刻只允许一个控制端拥有运动控制权，避免两个手机或键盘与手机同时驱动。
5. **新增协议握手与能力协商**：正式定义 `client_hello / server_hello / claim_control / release_control`，为协议版本、机器人编号、软件版本和功能能力预留统一入口。
6. **明确命令速度与实测速度的区别**：小程序显示“机器人接受的目标速度”和“机器人实际估计速度”时必须使用不同字段，不能混为一个 `vx/vy/wz`。
7. **安全参数以 RK3588 为最终权威**：小程序可以做 UI 限幅，但真正的速度、加速度、急停、超时等安全约束必须由机器人端再次执行。
8. **软件急停与物理急停严格区分**：软件急停是通信控制层的锁存安全状态，不能替代真实硬件物理急停。
9. **新增版本管理、风险矩阵、日志策略和交付物定义**。
10. **减少过度工程化**：首版不强制拆成大量微服务或多进程，优先保证链路简单、可靠、可调试；实机稳定后再做进程级隔离。

# 1. 项目背景与目标

本项目为自研 12 自由度四足机器人开发一套手机无线遥控系统。

机器人已具备强化学习运动控制能力，并已经能够通过键盘：

- `W / S`：前进 / 后退；
- `A / D`：左右横移；
- `Q / E`：绕 Z 轴旋转；

控制 MuJoCo 中的机器人。

当前目标不是重新设计运动控制器，而是将已有键盘控制能力抽象成统一速度接口，再通过微信小程序向机器人发送同样的速度目标。

最终链路：

```text
微信小程序
    ↓
WebSocket
    ↓
RK3588
    ↓
Command Manager
    ↓
Safety Manager
    ↓
VelocityCommand(vx, vy, wz)
    ↓
RL Policy Runtime
    ↓
┌───────────────┬────────────────┐
│ MuJoCo Backend│ Real Robot     │
│               │ Backend        │
└───────────────┴────────────────┘
```

核心目标：

1. 小程序直接产生 `vx / vy / wz`，不模拟 WASD/QE 键盘事件。
2. 键盘、小程序等都只是“命令输入源”。
3. MuJoCo 与真实机器人共享上层通信、命令管理、安全逻辑。
4. 从仿真切换到实机时，小程序协议原则上无需修改。
5. 网络通信异常时机器人必须自动进入安全状态。
6. 机器人内部实时控制不依赖小程序网络频率。
7. 整套系统具备可调试、可记录、可升级、可回滚能力。

## 2.2 当前最重要的技术缺口

正式接入 MuJoCo 和实机前，需要优先解决：

### 1. 命令超时与心跳超时必须完全分离

机器人端至少维护：

```text
last_command_rx_time
last_heartbeat_rx_time
```

规则：

- `cmd_vel` 只刷新 `last_command_rx_time`；
- `heartbeat` 只刷新 `last_heartbeat_rx_time`；
- heartbeat 持续正常时，旧的非零 `cmd_vel` 仍然必须按命令超时失效。

### 2. WebSocket 不能直接调用 RL Policy 或电机接口

网络层只能负责：

- 连接；
- 协议解析；
- 校验；
- 会话；
- 控制权；
- ACK；
- 遥测发送。

最终运动命令必须进入：

```text
Command Manager
    ↓
Safety Manager
    ↓
VelocityCommand
```

### 3. `seq` 必须以会话为作用域

每次重新建立 WebSocket 连接后创建新的 `session_id`。

`seq` 只在当前会话中要求单调递增。

不能使用“机器人全局永不回退 seq”，否则手机重连或重启后容易被误判。

### 4. 当前缺少独立的遥测发布机制

不能只在“收到手机消息”时才返回状态。

需要独立的 Telemetry Publisher 按固定频率向客户端推送机器人状态。

### 5. 当前缺少控制权机制

同一时刻只允许一个控制源真正驱动机器人。

MVP：

```text
NONE
KEYBOARD
WECHAT(session_id)
```

禁止两个控制源的速度叠加。

### 6. 当前缺少正式握手与版本协商

需要能够知道：

- 小程序版本；
- 协议版本；
- RK3588 软件版本；
- Policy 版本；
- 当前后端是 MuJoCo 还是实机；
- 机器人支持哪些功能。

# 5. 统一控制模型

## 5.1 VelocityCommand

所有上层输入最终统一为：

```text
VelocityCommand {
    vx: float
    vy: float
    wz: float
}
```

全系统坐标约定：

```text
X：机器人前方
Y：机器人左方
Z：机器人上方

vx > 0：前进
vy > 0：向左横移
wz > 0：绕 +Z 逆时针旋转

单位：
vx / vy：m/s
wz：rad/s
```

使用右手坐标系。

若当前 RL Policy 内部符号与上述约定不同，只允许在：

```text
RL Adapter
```

做一次转换。

不允许在：

- 小程序；
- WebSocket；
- Command Manager；

多处分别翻转符号。

---

## 5.2 CommandContext

机器人内部使用：

```text
CommandContext {
    command: VelocityCommand
    source: keyboard | wechat
    session_id
    seq
    received_at_monotonic
    expires_at_monotonic
}
```

客户端 `timestamp`：

- 用于 RTT 和日志；
- 不作为安全超时的最终时间来源。

机器人端安全超时统一使用 RK3588 本机单调时钟。

# 6. 通信协议 V1

## 6.1 总体原则

- WebSocket 作为当前遥控通信通道；
- JSON 用于第一版协议，便于调试；
- 所有消息都有 `type`；
- 每个客户端会话有独立 `session_id`；
- `seq` 在单个客户端会话内递增；
- 离散操作必须 ACK；
- 高频 `cmd_vel` 不逐包返回完整 ACK；
- 无效字段、错误类型、NaN、Infinity 必须拒绝；
- 限制单条消息最大尺寸；
- 未知但允许扩展的可选字段可忽略；
- 协议版本在握手阶段确定。

---

## 6.2 连接建立

### client_hello

```json
{
  "type": "client_hello",
  "protocol_version": 1,
  "client_type": "wechat_miniapp",
  "client_version": "0.1.0",
  "robot_id": "creeper-001"
}
```

### server_hello

```json
{
  "type": "server_hello",
  "protocol_version": 1,
  "session_id": "xxxx-xxxx",
  "robot_id": "creeper-001",
  "robot_software_version": "0.1.0",
  "policy_version": "model_xxx",
  "backend": "mujoco",
  "capabilities": [
    "cmd_vel",
    "stop",
    "estop",
    "estop_clear",
    "telemetry"
  ]
}
```

若协议版本不兼容：

```json
{
  "type": "error",
  "code": "PROTOCOL_VERSION_UNSUPPORTED"
}
```

# 7. 控制权机制

## 7.1 claim_control

```json
{
  "type": "claim_control",
  "seq": 10
}
```

成功：

```json
{
  "type": "command_ack",
  "seq": 10,
  "accepted": true,
  "result": "CONTROL_GRANTED"
}
```

失败：

```json
{
  "type": "command_ack",
  "seq": 10,
  "accepted": false,
  "result": "CONTROL_BUSY"
}
```

---

## 7.2 release_control

```json
{
  "type": "release_control",
  "seq": 11
}
```

释放控制权时：

1. 立即清空当前运动命令；
2. 输出零速度；
3. 控制源变为 `NONE`。

---

## 7.3 MVP 控制权规则

```text
NONE
  ↓ claim
WECHAT(session A)
```

另一客户端：

```text
WECHAT(session B)
```

可以连接并查看状态，但不能发送运动命令。

键盘调试阶段可由配置决定：

```text
control_source = keyboard
```

或：

```text
control_source = websocket
```

首版不做复杂抢占。

# 8. 小程序 → RK3588 协议

## 8.1 cmd_vel

固定周期发送“当前最新摇杆值”。

```json
{
  "type": "cmd_vel",
  "seq": 100,
  "timestamp": 123456789,
  "vx": 0.20,
  "vy": 0.00,
  "wz": 0.30
}
```

建议初始频率：

```text
20 Hz
```

原则：

```text
touchmove
    ↓
只更新本地目标值
    ↓
20 Hz timer
    ↓
发送最新 cmd_vel
```

松手 / stop / estop 必须绕过 20 Hz 定时器立即发送。

---

## 8.2 heartbeat

```json
{
  "type": "heartbeat",
  "seq": 101,
  "timestamp": 123456799
}
```

heartbeat 不能延长旧速度命令寿命。

---

## 8.3 stop

```json
{
  "type": "stop",
  "seq": 102
}
```

语义：

- 清空当前运动目标；
- 输出零速度；
- 不锁存；
- 后续新的有效 `cmd_vel` 可以重新开始运动。

---

## 8.4 estop

```json
{
  "type": "estop",
  "seq": 103
}
```

语义：

- 立即锁存软件急停；
- 清空所有运动目标；
- 拒绝新的运动和模式命令；
- UI 明确进入 ESTOP 状态。

软件急停不等于物理急停。

---

## 8.5 estop_clear

```json
{
  "type": "estop_clear",
  "seq": 104
}
```

机器人端只有在以下条件满足时接受：

- 物理急停未激活；
- 当前机器人没有致命故障；
- 当前会话拥有控制权；
- 摇杆目标为零；
- 机器人处于允许恢复的状态；
- 控制器处于 ready；
- 用户完成明确解除操作。

小程序建议：

```text
长按解除急停
```

而不是单击。

---

## 8.6 后续命令

第二阶段再增加：

- `stand`
- `sit`
- `lie_down`
- `mode_switch`
- `gait_switch`

高风险功能后置：

- `recover`
- `controller_switch`
- `parameter_update`

其中 `parameter_update` 不允许作为普通遥控接口任意修改控制参数。

# 9. RK3588 → 小程序协议

## 9.1 robot_state

建议 10～20 Hz。

需要明确区分：

### 机器人接受的速度目标

```text
applied_command
```

### 实际估计速度

```text
base_velocity
```

示例：

```json
{
  "type": "robot_state",
  "server_seq": 501,
  "timestamp": 123456900,
  "robot_state": "MOVING",
  "control_enabled": true,
  "active_source": "wechat",
  "estop": false,
  "last_cmd_seq": 100,

  "applied_command": {
    "vx": 0.20,
    "vy": 0.00,
    "wz": 0.30
  },

  "base_velocity": {
    "vx": 0.18,
    "vy": 0.01,
    "wz": 0.28
  },

  "imu": {
    "roll": 0.01,
    "pitch": -0.03,
    "yaw": 1.24
  }
}
```

如果实机暂时没有可靠速度估计器：

```text
base_velocity = null
```

禁止用“目标速度”假装“实际速度”。

---

## 9.2 controller_state

建议 2～5 Hz + 状态变化立即发送。

```json
{
  "type": "controller_state",
  "rl_policy": "running",
  "policy_version": "model_xxx",
  "policy_hz": 50,
  "active_source": "wechat",
  "backend": "mujoco",
  "command_timeout": false
}
```

---

## 9.3 telemetry_power

建议 1～2 Hz。

```json
{
  "type": "telemetry_power",
  "battery_percent": 78,
  "battery_voltage": 47.6,
  "battery_current": 3.2
}
```

暂时无法获取的数据允许：

```text
null
```

不要伪造。

---

## 9.4 telemetry_compute

建议 1 Hz。

```json
{
  "type": "telemetry_compute",
  "cpu_percent": 42,
  "gpu_percent": 35,
  "memory_percent": 51,
  "soc_temperature": 63.5
}
```

---

## 9.5 telemetry_network

建议 1～2 Hz。

```json
{
  "type": "telemetry_network",
  "rtt_ms": 31,
  "wifi_rssi_dbm": -52,
  "interface": "wlan0"
}
```

---

## 9.6 heartbeat_ack

```json
{
  "type": "heartbeat_ack",
  "seq": 101,
  "client_timestamp": 123456799
}
```

小程序：

```text
RTT = 当前手机时间 - client_timestamp
```

不要求手机与 RK3588 时钟同步。

---

## 9.7 fault

统一故障事件：

```json
{
  "type": "fault",
  "severity": "WARNING",
  "code": "CMD_TIMEOUT",
  "message": "速度指令超时，机器人已停止",
  "recoverable": true
}
```

严重级别：

```text
INFO
WARNING
ERROR
FATAL
```

小程序业务逻辑必须根据：

```text
code
```

判断，而不是根据自然语言 `message` 判断。

# 10. 状态机设计

网络状态与机器人状态严格分开。

---

## 10.1 Connection State

小程序连接状态：

```text
DISCONNECTED
    ↓
CONNECTING
    ↓
CONNECTED
    ↓
AUTHENTICATED
    ↓
CONTROL_GRANTED
```

异常：

```text
RECONNECTING
TIMEOUT
ERROR
```

规则：

- 未到 `CONTROL_GRANTED` 不允许发送非零 `cmd_vel`；
- 断线立即本地归零；
- 重新连接后必须重新取得控制权；
- 旧会话失效。

---

## 10.2 Robot State

MVP：

```text

STANDBY
```

## 12.3 stop 与 estop

### stop

目标：

```text
正常减速 / 停止运动
```

机器人保持 RL 控制器正常运行。

### software estop

目标：

```text
立即禁止新的运动命令
```

MVP 建议：

- 锁存；
- 目标速度强制为零；
- 若控制器健康，保持安全站立；
- 不自动执行趴下；
- 不自动解除。

不要在第一版中让软件急停自动执行复杂姿态动作。

### physical estop

必须属于独立硬件安全链路。

不能被：

- 小程序；
- WebSocket；
- 软件；

远程解除。

# 23. 风险分析

| 风险 | 后果 | 优先级 | 处理 |
|---|---|---:|---|
| heartbeat 延长旧 cmd | 机器人失控持续运动 | 极高 | 两个独立 watchdog |
| 网络线程阻塞控制线程 | 控制周期抖动 / 失稳 | 极高 | 解耦、最新值缓存 |
| 两个客户端同时发送 | 指令争抢 | 高 | 独占控制权 |
| 小程序误触 | 意外运动 | 高 | 控制解锁、死区、急停 |
| seq 全局化 | 重连后无法控制 | 中 | session 级 seq |
| 手机时间错误 | 错误超时 | 中 | RK3588 monotonic |
| 目标速度当作实测速度 | UI 误导 | 中 | applied / measured 分开 |
| 长期硬编码 token | 控制权限泄露 | 高 | 正式配对 / session |
| 高频日志写盘 | 性能下降 / 存储耗尽 | 中 | 采样 + rotation |
| 遥测频率过高 | 网络和 CPU 浪费 | 低 | 分频发布 |
| 直接让 estop 自动趴下 | 姿态动作风险 | 高 | MVP 仅锁存+零速 |
| 配置散落代码 | 实机参数不可追踪 | 中 | YAML + config version |

# 29. 最终验收标准

项目达到“可正式使用”至少应满足：

- 小程序直接发送 `vx / vy / wz`；
- 不模拟键盘按键；
- 键盘和微信共享统一 `VelocityCommand`；
- 网络线程不直接驱动 RL 或电机；
- 命令超时与 heartbeat 超时完全独立；
- 一个机器人只有一个 active controller；
- session 级 seq 正常；
- MuJoCo 与实机只在 Backend 层不同；
- 小程序显示机器人确认状态而非仅显示本地状态；
- applied command 与实际速度分开；
- stop / timeout / disconnect 可确定性归零；
- 软件急停锁存；
- 物理急停独立；
- 非控制权客户端无法驱动机器人；
- 网络和遥测异常不阻塞 RL / 低层控制；
- 所有安全参数在 RK3588 再次校验；
- 具备日志、错误码、配置、版本信息；
- 具备协议测试、网络测试和实机安全测试；
- 具备升级与回滚方案；
- 同一套小程序和通信架构可以同时支持 MuJoCo 与真实机器人。
