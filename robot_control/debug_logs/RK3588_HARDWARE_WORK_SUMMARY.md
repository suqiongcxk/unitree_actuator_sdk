# 四足机器人 RK3588 实机端工作总结（面试版）

> 依据当前 `CXK` 分支中的控制源码、README、模型交付清单、串口协议及实机记录整理。  
> 状态口径：**已实现**表示代码已经存在；**已验证**表示已有软件、仿真或实机记录；**已设计待接入**表示只有设计/协议或基础模块，尚未进入整机控制链路。

## 第一部分：项目整体架构

这是我从机械模型、电机通信、状态估计、强化学习策略部署到安全遥控逐步搭建的一套 12 自由度自研四足机器人实机系统。机器人使用 Orange Pi 5 Pro（RK3588）作为上位主控，12 台 Unitree GO-M8010-6 作为关节执行器，JY901S 作为机体 IMU。RK3588 不只是“运行神经网络”，还负责整机启动、机械限位标定、传感器采集、四路 RS-485 调度、状态有效性判断、ONNX 推理、关节目标转换以及故障后的统一阻尼停机。

当前实际控制数据流是：

```text
键盘/FIFO速度命令 [vx, vy, yaw_rate]
        ↓
VelocityCommandManager：范围检查、超时、斜坡平滑
        ↓
JY901S IMU + 12台M8010反馈(q/dq/tau/temp/MError)
        ↓
Complementary状态估计 + 足端运动学/接触/机体速度估计
        ↓
构造48维observation
        ↓
ONNX Runtime在RK3588 CPU执行Actor推理
        ↓
12维raw action
        ↓
q_des = default_joint_position + 0.25 × raw_action
        ↓
有限值、关节范围、增益和运动指标检查
        ↓
URDF关节坐标转换为电机坐标
        ↓
4路RS-485线程并行下发位置、Kp、Kd
        ↓
12个关节执行并回传状态，形成下一帧闭环
```

计划中的新遥控数据流是“手机 Wi-Fi → 自研 ESP32-S3 PCB → 3.3 V TTL UART → RK3588”。其中 UART Protocol V1 和纯内存编解码/流解析器已经完成，但真实 `/dev/ttyS1` 串口读取、控制权状态机和 `robot_control` 接入仍未完成，不能把它描述成已投入使用。

## 第二部分：RK3588 的职责

我把 RK3588 设计成机器人唯一的运动控制主控，主要承担以下任务。

1. **启动与初始化。** `robot_control_main.cpp` 解析模型、日志、状态估计器和诊断参数；`RobotController::initialize()` 依次检查 12 个电机 ID 是否完整唯一、初始化 JY901S、执行机械限位标定、创建四路并行总线并加载 ONNX。正常模式下，标定不足 12/12 会拒绝进入控制。
2. **机械零点与站立。** 工程按机械限位建立电机坐标到 URDF 坐标的零点和方向映射。四条腿分左右两批标定，同批两腿并行；标定后的四个大腿预定位已经改为四路并行。随后以 smoothstep 从反馈真实位置平滑过渡到默认站姿，再用 2 s、100 帧平滑混合让 ONNX 接管。
3. **多线程实时任务。** 系统共管理 7 条关键线程：IMU 200 Hz、状态估计 50 Hz、神经网络 50 Hz，以及四条独立电机总线各 500 Hz。各周期使用 `CLOCK_MONOTONIC` 和绝对时间睡眠，并统计最大周期间隔、执行时间和 deadline miss。
4. **线程间数据交换。** IMU→估计器、估计器→NN 使用“短锁发布、值快照读取”；电机总线状态和命令使用 mutex 保护的小结构体拷贝。I2C、ONNX 推理和串口收发都不在共享锁内执行，避免慢 I/O 阻塞其他线程。
5. **状态采集与整理。** 将 12 台电机的位置、速度、力矩、温度、错误码、反馈时间和连续失败次数按 motor ID 整理；再转换到统一 URDF 坐标系。IMU 提供四元数、加速度和角速度，软件执行四元数归一化、符号连续、陀螺零偏校准和 15 Hz 低通。
6. **状态估计。** 当前默认后端是 `ComplementaryStateEstimator`，不是 Linear KF。它融合 IMU、腿部正运动学、关节速度和由关节力矩/雅可比估算的足端支撑力，输出投影重力、机体系速度、接触置信度和机身高度。Linear KF 已实现为可选后端 `--estimator kalman`，但不能把它说成当前默认实机算法。
7. **策略与执行。** RK3588 使用 ONNX Runtime CPU Provider 推理，将 12 维 Actor 输出转换为位置目标和固定 PD 增益，再异步提交给四路电机线程。
8. **健康监控与退出。** 主线程监控 IMU、估计器、NN 和电机反馈，首个故障锁存后停止产生新运动目标，四路总线立即切换为 12 电机阻尼模式，并回收全部线程。

## 第三部分：电机与 RS-485 通信

### 1. 为什么使用四路总线

GO-M8010-6 的通信是主机逐台发送、逐台等待反馈的半双工事务。若 12 台电机全部串在一条总线上，一个周期要连续完成 12 次收发，单台超时或迟到回复还会拖累整机周期并造成后续 ID 错位。工程按“一条腿一条总线、每路三台电机”拆成四路：这样四条腿可并行通信，将单路事务数从 12 降为 3；故障也能按腿隔离，方向控制 GPIO 和串口时序更容易诊断。

### 2. 总线和关节映射

| 腿 | 串口 | DE/RE GPIO | 电机ID | 关节 |
|---|---|---:|---|---|
| FL 左前 | `/dev/ttyS6` | GPIO39（chip1:7） | 0 / 4 / 8 | hip / thigh / calf |
| FR 右前 | `/dev/ttyS4` | GPIO63（chip1:31） | 1 / 5 / 9 | hip / thigh / calf |
| RL 左后 | `/dev/ttyS7` | GPIO35（chip1:3） | 2 / 6 / 10 | hip / thigh / calf |
| RR 右后 | `/dev/ttyS0` | GPIO133（chip4:5） | 3 / 7 / 11 | hip / thigh / calf |

全局数组采用 Z 字顺序：`[FL,FR,RL,RR] hip`、`[FL,FR,RL,RR] thigh`、`[FL,FR,RL,RR] calf`，数组下标严格等于 motor ID。启动时程序会拒绝重复、越界或缺失 ID，避免“模型第 i 个输出”发给错误关节。

### 3. 通信实现

`ParallelBus` 为每条总线维护三个命令/反馈槽。NN 线程只更新槽内目标；500 Hz 总线线程复制本周期命令后，依次完成三台电机的 TX→切换方向→RX。GPIO 采用 Linux GPIO v2 ioctl；发送完成通过 `TIOCOUTQ` 与 `TIOCSERGETLSR(TEMT)`判断，避免 `tcdrain()` 在 RK3588 上带来的长阻塞。

M8010 控制帧为 17 Byte，包含包头、ID/模式、目标力矩、速度、位置、Kp、Kd 和 CRC16；反馈帧为 16 Byte，包含实际力矩、速度、位置、温度、`MError`、可选压力值和 CRC16。库内部按 6.33:1 减速比处理位置/速度量纲；当前力矩反馈根据已有标定路径转换后用于足端力估算。

接收端只在“长度为 16 Byte、CRC 正确、返回 ID 与请求 ID 一致”时覆盖最近有效反馈和时间戳。短帧、零字节超时、CRC 错误、wrong-ID 分别计数；失败帧不会用未初始化数据覆盖旧状态。发送每台电机前还会清理迟到字节，防止上一台回复被下一台误读。

正常位置控制使用 FOC 模式。工程也实现了 BRAKE 命令和 `setDamping()`；发生急停时，`ParallelBus` 内部锁存优先级最高的阻尼状态，即使线程已经复制了旧位置命令，实际发送前仍会将其覆盖为 `q=0、Kp=0、dq=0、tau=0、Kd=0.136`。程序保持发送约 200 ms 后再回收线程。这里的“阻尼停机”不是切断电源，而是受控耗散关节速度。

## 第四部分：强化学习策略部署

训练端先保存 PyTorch checkpoint，再导出只包含 Actor 的 ONNX。当前默认模型由 CMake 固定为版本化路径中的 V30/model_1299，模型 SHA256 和 checkpoint SHA256 均保存在交付目录。部署前用 golden vectors 对 Python 与 C++ 的 observation、ONNX 输出和 `q_des` 做逐元素对拍；当前记录中的最大误差为 `10^-6` 量级。

ONNX Runtime 配置为 CPU Execution Provider、单线程 intra-op、全图优化。加载时检查模型接口，当前契约为：输入名 `obs`、`float32 [1,48]`；输出名 `actions`、`float32 [1,12]`；opset 18。

48 维 observation 的真实顺序是：

| 范围 | 内容 | 单位/语义 |
|---|---|---|
| 0–2 | 机体系线速度 | m/s |
| 3–5 | 机体系角速度 | rad/s |
| 6–8 | 机体系投影重力 | 单位向量，水平约 `[0,0,-1]` |
| 9–11 | `vx, vy, yaw_rate` | m/s、m/s、rad/s |
| 12–23 | `joint_position-default_pose` | rad |
| 24–35 | 关节速度 | rad/s |
| 36–47 | 上一帧 Actor 原始 action | 无量纲 |

12 维 action 顺序与 motor ID 相同。默认姿态为：

```text
[0.1,-0.1,0.1,-0.1, 0.8,0.8,1.0,1.0, -1.5,-1.5,-1.5,-1.5] rad
```

目标生成公式是：

```text
q_des[i] = default_joint_position[i] + 0.25 × raw_action[i]
```

正常 PD 增益为 `Kp=0.625、Kd=0.0125`。上一帧 action 必须是 Actor 的原始输出，而不是缩放后的 `q_des` 或安全层回退值，因为训练时策略用它表达动作历史；语义错误会让输入分布改变，形成不必要的振荡或步态退化。

需要准确说明的是：`PolicyObservationBuilder` 当前按训练接口直接拼接数值，没有额外 observation normalization 或 clipping；raw action 也没有通用裁剪。工程已有三类连续性处理：速度命令斜坡、启动时 2 s 平滑接管、输出跳变/目标速度监测。当前“单关节目标速度、反馈速度、12关节聚合变化”和 jump-only 都处于 `MONITOR_ONLY`，不是强制 action rate limiter；NaN/Inf、关节目标越界和非法 Kp/Kd 仍会触发停机。这个边界在面试中必须如实表达。

## 第五部分：完整控制循环和数据流

以第 N 个 20 ms 策略周期为例：

1. 四个 500 Hz `ParallelBus` 线程持续独立轮询电机。每个反馈经过帧长、CRC、ID检查后更新 `MotorState`；失败则保留最近有效值并增加失败计数。
2. 200 Hz IMU 线程读取 JY901S，将加速度、角速度和四元数通过快照缓冲发布。
3. 50 Hz 状态估计线程取得最新 IMU 快照，并从四条总线复制 12 个关节状态。它按标定零点和方向把电机坐标变换为 URDF 坐标，计算每个反馈的年龄。
4. 状态估计器检查 IMU 时间、四元数、陀螺值、12关节有限性、`MError` 和 100 ms 电机反馈新鲜度。无效状态不会进入新的策略控制。
5. 默认 Complementary 后端计算投影重力、滤波角速度、足端位置/速度和法向支撑力；利用可信支撑足约束估计机体速度，并把世界系速度旋转到机体系。
6. NN 线程从 `VelocityCommandManager` 取得经过限幅和斜坡后的 applied command。命令范围为三轴 `[-1,1]`，默认 watchdog 为 500 ms，单条命令最长保持 5 s；超时目标变为零并按 `0.5/0.5/1.0` 的线加速度/角加速度平滑回零。
7. `PolicyObservationBuilder` 按固定顺序拼出 48 维数组，ONNX Runtime 执行一次 Actor 推理，并保存 raw action 作为下一帧 observation 的 36–47 维。
8. 用 `default_pose+0.25×action` 生成 12 个 URDF 关节目标，附加固定 Kp/Kd。启动后的前100帧还会与默认站姿做 smoothstep 混合。
9. `ValidatingPolicy` 检查有限值、机械范围（默认向内保留 0.05 rad）、Kp/Kd 和相邻目标变化。硬错误时保持上一帧安全目标但不再下发新位置命令，同时请求统一阻尼停机。
10. 通过检查后，控制器按 motor ID 将 URDF 目标转换回各电机坐标，写入相应总线槽。四路 500 Hz 线程继续重复这个目标，直到下一次 50 Hz 策略更新。
11. 所有线程按绝对单调时钟进入下一周期；可选 CSV 日志保存估计状态、raw/limited/applied command、完整 observation、raw action 和最终 target，便于离线复盘。

## 第六部分：遥控与通信协议

### 已投入使用：本机/SSH键盘链路

当前多键实机遥控由Windows端`remote_control/keyboard/pc_keyboard_velocity_client.py`读取按下/松开状态，通过SSH桥接和权限受控的FIFO `/tmp/creeper_velocity_command.fifo`向唯一的`robot_control`进程发送完整三轴速度。SSH终端版`remote_control/keyboard/keyboard_velocity_console.py`保留为单键备用工具。FIFO只传高级速度目标，所有键盘程序均不接触电机。详细按键、速度档位和失联行为见`remote_control/docs/KEYBOARD_REMOTE_CONTROL.md`。

### 已设计并完成基础解析器、尚未实机接入：ESP32-S3 UART

物理层定义为 RK3588 `UART1_M1`：GPIO1_B7/物理7脚是 RX，GPIO1_B6/物理15脚是 TX，对应 `/dev/ttyS1`；双方 3.3 V TTL、TX/RX交叉、共地，115200-8-N-1、无流控。该 UART 不与四路电机串口或 I2C IMU冲突。

Protocol V1 帧为：`AA 55` 同步字、版本、消息类型、payload长度、32位 sequence、最长48 Byte payload、CRC16。字节序为 little-endian；CRC 使用 CCITT-FALSE（poly `0x1021`、init `0xFFFF`），覆盖 version 到 payload，不含同步字和 CRC。流解析器已处理噪声、拆包、粘包、错误版本、超长和 CRC 错误，并实现 sequence 环回新旧判断。

协议定义了 HELLO/ACK、CLAIM/RELEASE_CONTROL、CMD_VEL、STOP、ESTOP、ESTOP_CLEAR、HEARTBEAT、STATUS。CMD_VEL 使用三个 int16，单位分别为 mm/s、mm/s、mrad/s，避免 UART 裸传 float 的 NaN、ABI和字节序问题。控制权设计保证 KEYBOARD 与 SERIAL 不叠加；串口不能抢占键盘。STOP 是保留控制权的平滑回零，ESTOP 是锁存阻尼停机，ESTOP_CLEAR 必须校验 session nonce、零命令和机器人状态。

设计的双 watchdog 为：CMD_VEL 250 ms、heartbeat 600 ms。心跳不能刷新旧速度；命令超时平滑归零，链路超时归零并释放 SERIAL owner，内部硬故障或 ESTOP 才进入阻尼停机。**目前这些会话、控制权、watchdog和状态回传仍是协议设计，RK3588真实串口服务尚未连接到 `VelocityCommandManager`。**

## 第七部分：安全机制

强化学习策略不能“输出什么就直接执行什么”，因为仿真中的关节约束、接触、供电和延迟都比实机理想。当前工程的安全层包括：

- 上电先做陀螺静态校准、12关节机械限位标定和标定结果检查；任何标定失败都禁止站立。
- 大腿预定位、开环站立和 ONNX 接管分阶段平滑完成，避免从机械限位直接跳到蹲伏策略姿态。
- 速度命令拒绝 NaN/Inf，三轴限制为 `[-1,1]`，有 500 ms watchdog 和 slew rate，失联后不是保持上一速度。
- NN 输出检查 NaN/Inf、关节机械范围和 Kp/Kd；越界目标不下发。当前最近一次实机日志中 joint[9] 目标越过机械上限，系统正确锁存 `NN_COMMAND_INVALID detail=9`并阻尼退出。
- 电机反馈仅接受完整、CRC正确且ID匹配的帧；偶发单帧丢失不立即误停，但最近有效反馈超过100 ms会使状态无效，连续无效后停机。
- 非零 `MError`、90°C过温、IMU/估计/NN线程心跳超过100 ms、状态流中断都会锁存首个根因。
- Ctrl+C、主终端 `s`、键盘遥控 X，以及内部故障最终走同一安全关闭路径；12台电机进入 `Kd=0.136` 阻尼，关闭阶段打印全部 MError 和总线时序。
- 运动安全层会计算单关节目标变化率、实际反馈速度、多关节同步变化和12关节总变化。不过当前三项 enforce 开关均为 false，只记录不拦截，不能在面试中说成已启用硬限速。
- 新 UART 协议进一步设计了 control ownership、STOP、锁存 ESTOP 和显式 ESTOP_CLEAR，但尚未完成整机接入。

## 第八部分：Sim2Real 接口一致性

我把 Isaac Lab、MuJoCo 和 RK3588 之间最容易出错的接口固定成一份契约：

1. **关节顺序一致。** 三端统一采用 hip 0–3、thigh 4–7、calf 8–11，腿序 FL、FR、RL、RR。
2. **坐标和单位一致。** 机体系为 +X前、+Y左、+Z上；关节位置 rad、速度 rad/s、力矩 N·m，速度命令为 m/s 和 rad/s。
3. **零点和方向一致。** 实机通过机械限位标定建立 `q_urdf=direction×(q_motor-zero_offset)`；位置、速度、力矩使用对应方向变换。
4. **模型资产一致。** 当前交付绑定 Creeper20260906 URDF、USD 和 MJCF，髋关节位置、质量和足端半径在共享参数中留有版本记录。
5. **策略接口一致。** 48维 observation 的顺序、default pose、12维 action 顺序、`action_scale=0.25`、50 Hz 推理和 previous raw action 语义保持一致。
6. **命令与动作处理一致。** 实机没有私自增加 observation 归一化/裁剪；若仿真没有对应处理，也不能只在实机端偷偷改。启动接管和遥控速度斜坡属于部署安全层，应在仿真测试中复现其时序。
7. **数值对拍。** golden-vector 测试直接比较训练端 observation、ONNX raw action 和 C++ `q_des`；模型文件用 SHA256 确认，避免“文件同名但内容不同”。

这些细节一旦不一致，常见结果不是简单的精度下降，而是左右腿错位、正负号反向、默认姿态偏移、上一帧动作语义错误、模型输出突跳或某个关节持续撞机械限位。最近 V30 实机换向过程中出现 joint[9] 越界，也说明仿真通过不能代替实机过渡工况验证。

## 第九部分：实际调试中解决的问题

我在这部分真正解决的不是单一算法，而是一整条实机链路的问题：

- 将 12 电机按腿拆成四路 RS-485，并实现并行总线线程、快速方向切换、反馈统计与迟到字节清理。
- 修复未初始化 `MotorData.motorType` 导致的短帧/CRC异常，并确保坏帧不覆盖最近有效状态。

## A. 2分钟口述稿

我做的是一台12自由度自研四足机器人的实机控制系统，RK3588是整机主控。底层有12台Unitree M8010关节电机，我没有把它们全挂在一条RS-485上，而是按四条腿拆成四路，每路三台，四个线程各以500 Hz通信。这样可以把12次串行事务拆成四路并行，也能把通信故障定位到具体腿和具体电机。

RK3588上还有200 Hz的JY901S IMU线程、50 Hz状态估计线程和50 Hz策略线程。电机反馈包含位置、速度、力矩、温度和错误码；我把它们经过机械零点和方向映射统一到URDF坐标。状态估计目前默认用互补式前端和腿式里程计，结合IMU、足端运动学以及由关节力矩和雅可比估计的足端力，得到投影重力、机体速度和接触状态。

强化学习策略在服务器用PyTorch训练，导出ONNX后在RK3588上用ONNX Runtime CPU推理。网络输入是48维，包括机体线速度、角速度、投影重力、三维速度命令、12维相对关节位置、12维关节速度和上一帧12维原始action；输出12维action，再按默认姿态加0.25倍action生成关节位置目标。模型接口通过SHA256、manifest和golden vectors做过Python/C++逐帧对拍。

我比较重视实机安全。机器人上电先完成IMU静态校准、12关节机械限位标定、平滑站立和2秒策略接管。运行中检查CRC、ID、反馈年龄、MError、90度过温、状态流和线程心跳；策略目标还检查有限值、机械限位和PD增益。任何硬故障都锁存首个原因，停止下发新运动目标，并让12台电机统一进入Kd为0.136的阻尼模式。

目前系统已经完成零命令稳定站立、ONNX实机闭环和键盘速度遥控，也开展了非零速度试走。当前还在解决换向瞬态下个别策略目标越界和长期可靠性问题。下一步遥控会从键盘升级为手机到ESP32-S3、再通过3.3 V UART接RK3588；协议和解析器已经完成，但真实串口整机接入仍在开发。

## B. 面试官可能追问的15个问题

1. **为什么选择RK3588？**  
   它能同时提供ARM多核CPU、足够的UART/I2C/GPIO资源和Linux生态，能够在一块板上完成多路硬实时性较强的I/O调度、状态估计、日志和50 Hz ONNX推理。项目当前用CPU Provider，尚未依赖NPU。

2. **为什么用四路RS-485，而不是一条总线挂12台？**  
   M8010是逐台请求响应。单总线12台会放大串行延迟和单点超时影响；四路按腿并行后，每路只有三次事务，同时获得更好的故障隔离。

3. **如何保证50 Hz策略周期？**  
   NN线程独占ONNX Session，推理使用单线程intra-op；线程按 `CLOCK_MONOTONIC` 绝对时间睡眠。慢速串口在独立500 Hz线程运行，NN只做加锁拷贝，不等待硬件收发，并记录周期和执行超时。

4. **为什么电机总线设置500 Hz，策略只有50 Hz？**  
   策略每20 ms更新一次目标，但电机通信需要高频重复发送PD目标并及时取得反馈。500 Hz总线把高级策略频率与底层执行/监控频率解耦。

5. **ONNX为什么适合部署？**  
   它把训练框架与运行时解耦，RK3588不需要完整PyTorch环境；接口形状固定，可用ONNX Runtime优化，并方便用golden vectors做跨语言数值对拍。

6. **48维输入具体是什么？**  
   3维机体系线速度、3维角速度、3维投影重力、3维速度命令、12维相对默认姿态的关节位置、12维关节速度、12维上一帧原始action。

7. **上一帧action为什么重要？**  
   它是训练时的状态历史，使Actor能够感知动作连续性。实机如果换成上一帧q_des或安全层输出，就改变了训练分布，可能导致振荡或步态失真。

8. **电机丢包时怎么办？**  
   单次CRC失败只计数并保留最近有效反馈，避免500 Hz链路偶发错误让50 Hz控制误停；但反馈年龄超过100 ms会判无效，连续无效后统一阻尼退出。

9. **如何防止策略输出异常？**  
   先检查模型接口和NaN/Inf，再把action转换为q_des，检查机械限位、PD增益和目标变化指标。硬错误帧不下发，保持最后安全目标并立即请求阻尼停机。

10. **当前有没有action rate limiter？**  
    严格说没有常态强制raw-action rate limiter。已有速度命令slew rate、启动平滑接管和目标变化监测；当前目标速度等几项处于monitor-only。我会明确区分，后续根据实测阈值决定是否恢复强制执行。

11. **遥控断连怎么办？**  
    当前键盘/FIFO有deadman和500 ms命令watchdog，超时速度目标平滑回零。新UART协议设计了独立250 ms命令和600 ms心跳watchdog，避免“心跳还在就永久保持旧速度”，但该链路尚未接入实机。

12. **STOP和ESTOP有什么区别？**  
    STOP是速度平滑回零并可保持站立控制；ESTOP锁存系统故障并进入12电机阻尼退出，通信恢复不会自动清除。ESTOP_CLEAR需要显式操作和状态检查。

13. **Sim2Real最大的问题是什么？**  
    不是ONNX能不能运行，而是接口和真实动力学：关节顺序、正负号、零点、单位、上一帧action、接触、摩擦、供电和通信延迟。任何一项偏差都可能让仿真稳定策略在实机撞限位。

14. **如何验证状态估计效果？**  
    我分别验证了水平投影重力、Roll/Pitch/Yaw方向、陀螺静态偏置、单/双腿卸载、腾空、机体移动速度方向和模拟打滑降置信；静态足端法向力和约10 kg重量也做了闭合检查。当前默认不是Kalman，而是Complementary后端。

15. **项目中最有代表性的工程问题是什么？**  
    一次策略异常后旧逻辑直接跳到默认站姿，安全回退反而制造更大目标跳变。我把它改成危险帧不提交、不写总线、保持最后安全目标并立即进入统一阻尼停机，之后又用故障注入、零命令接管和总线回归验证。
